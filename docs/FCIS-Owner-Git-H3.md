# H3 — owner-controlled Git acceptance and promotion

**Status:** SOURCE-TESTED on disposable Ubuntu Git origins, protected Git review pending, 18 November 2026. **Authority:** [FCIS maintenance plan](FCIS-Maintenance-Hook-CI-Plan.md), [Git release policy](FCIS-Git-Release-Policy.md), canonical [stack](../FCIS-STACK.md). **Purpose:** protect the canonical source Git `main` independently of GitHub by means of ordinary Git, POSIX `/bin/sh`, signed owner approval, a constrained isolated runner, and independently recorded acceptance. **Not** a new OAuth/FCIS service, CI vendor or client authorization mechanism.

## Reviewed source components

- [`.githooks/pre-receive`](../.githooks/pre-receive): to be **installed separately** in an owner-owned **bare Git origin** as `hooks/pre-receive`. Rejects all direct writes to `main`, unknown tags/refs, candidate deletion/updates and non-fast-forward work branch updates. Accepts only creation of immutable `refs/heads/candidates/<safe-id>` and controlled `refs/heads/work/<safe-id>`. A network client cannot rely on overriding this server-side hook.
- [`scripts/fcis-git-approve.sh`](../scripts/fcis-git-approve.sh): owner-device script that creates a short-lived **OpenSSH Ed25519 signed approval**, without putting an owner's private signing key on the Git receiver or in the repo. Sign exact repository identity, candidate ref and SHA, expected old `main`, reviewed policy digest and expiry.
- [`scripts/fcis-git-promote.sh`](../scripts/fcis-git-promote.sh): separately installed reviewed operator script, **never executed from the receive hook**. Verifies the signed approval against an **administrator-owned `authorized_signers`** allowlist and exact current ref identities. Checks pinned CI-validator file hashes, makes an isolated checkout with Git configuration scrubbed, runs [H2 source CI](../scripts/fcis-ci.sh) inside Bubblewrap as unmapped UID 65534 with no network, read-only candidate checkout and restricted host filesystem, bounded CPU/file descriptors/file size and 180s wall clock. Writes source-check log digests and prepared receipt before atomic `git update-ref main NEW OLD`; after readback writes final receipt.
- [`skills/tests/test_fcis_git_h3.py`](../skills/tests/test_fcis_git_h3.py): offline, disposable bare-origin matrix with ephemeral signing keys. Tests direct-main rejection, immutable candidates, unsafe refs, signatures/expiry, policy change, stale main, pinned CI files, failing source and successful promotion. On a host without `bwrap` the H3 sandbox-specific cases **skip**; a green GitHub CI alone cannot establish Ubuntu sandbox acceptance.

## Security and required *separate* OS identities

**No live installation is authorized by these source files alone.** On the selected Ubuntu owner host, prove dedicated **receiver, isolated test and operator identities** with minimum filesystem privileges *before* binding a listener/SSH forced command or treating the bare origin as protected. The receiver can accept candidate Git objects/refs via restricted `git-receive-pack`, but cannot invoke promotion or access the owner's signing key. The operator alone can read the reviewed policy and atomically promote; the candidate test identity has neither protected Git-write permissions nor production issuer keys/Store mounts. The owner signing key stays on a separate trusted owner device.

A server `pre-receive` protects against ordinary Git pushes, **not a shell user who can freely edit the bare repo**. Do not grant arbitrary shell command execution to a receiver identity. Use forced Git commands and tight allowed paths. A separate operator, audited OS service permissions and out-of-band owner key storage are mandatory for claiming authority against a compromised receiver. The exact OS provisioning is a distinct owner-host action with administrative permission and account readback. This document does not instruct bypassing a host command policy or modifying the existing authorized FCIS Host.

**Review the installed bytes:** do not execute an incoming branch's `.githooks/pre-receive` or `scripts/fcis-git-promote.sh` as an authority. Install only a reviewed, immutable, locally owned copy of those files from an accepted source revision. Pin the approved CI binary/input scripts in `policy/trusted-files.sha256`; promoting a candidate that edits these requires a separate reviewed *policy-revision authorization*, not self-referential acceptance. Keep the owner-controlled `repository-id`, `authorized_signers`, hashes and the receipt root out of the writable candidate/receiver namespace, with no symbolic links.

## Read-only preparation (no host deployment)

1. Resolve the actual **full-history** organization clone and source SHA; inspect `git rev-parse --is-shallow-repository` and refuse an incomplete shallow seed. Never seed an authoritative origin by copying an existing recovery mirror and silently turning it into a writable Git receiver.
2. On an explicitly approved isolated volume/host under separate administrator control, initialize or clone a **new** bare Git repository with exact initial `main`, verify `git fsck --full`, record its `refs/heads/main`, and set an exact unique `fcis.repositoryID`. This is the approved bootstrap, not a new production issuer deployment.
3. Install `hooks/pre-receive` from reviewed source and verify `core.hooksPath` has not been redirected. Install `fcis-git-promote.sh` *outside* the bare repo; keep it unavailable to the receiver service. Create a private policy directory with `repository-id`, `authorized_signers` containing the reviewed owner **public** Ed25519 identity, `trusted-files.sha256` containing SHA-256 digests for `scripts/fcis-ci.sh`, `skills/skillctl.py`, `skills/plugin_projection.py` and `skills/tests/test_fcis_posix_ci.py`, and a writable-by-operator-only `receipts/` directory. Never store private keys or user data in Git.
4. Ensure Git candidate source can only be committed through reviewed `pre-receive`. Select an immutable candidate ref and old SHA via independent readback (not chat claims), then **on the owner's separate device** create the short-lived detached signature using the existing script and owner key. The operator accepts that exact signed pair, confirms the verifier policy and source head, executes the isolated H2 CI without other credentials, and performs compare-and-swap promotion. An incorrect digest/ref/expiry, failed test or changed `main` refuses the transaction.
5. Independently read back the main ref, receipts and hashes from a separate read-only clone. Clone a retained backup/bundle into an isolated path and verify `git fsck`. Keep GitHub mirror/ruleset **unchanged** until this passes on the owner-controlled origin *and* backup/restore is independently demonstrated. Only then plan controlled mirror/fallback promotion; no implicit vendor cutover.

## Approval format and example (owner-operated)

For a reviewed candidate `refs/heads/candidates/h3-review`, exact full `candidate SHA`, current `main SHA`, and the SHA-256 digest of the installed policy's `trusted-files.sha256`:

```sh
sh scripts/fcis-git-approve.sh /owner/secure/ed25519   Fountain-Coach/.github refs/heads/candidates/h3-review   CANDIDATE_FULL_SHA EXPECTED_MAIN_FULL_SHA TRUSTED_POLICY_SHA256   /owner/private/approval-h3.txt
```

This writes `approval-h3.txt` and `approval-h3.txt.sig`. The private key stays on the owner device. Separately the authorized operator invokes the reviewed `fcis-git-promote.sh` with `BARE_REPO POLICY_DIRECTORY CANDIDATE_REF CANDIDATE_SHA EXPECTED_MAIN_SHA APPROVAL_FILE`. Approval expires after 10 minutes. **Never** place a real signing key, approval or receipt inside an unreviewed branch or a prompt.

## Acceptance matrix

| Gate | Required independent proof |
| --- | --- |
| Source shell syntax | `sh -n` for receive/approval/promotion and H2 runner |
| Immutable ingress | Direct `main`, unknown refs, candidate mutation/deletion refused; one new candidate accepted |
| Owner authority | Valid detached Ed25519 approval accepted; tampering, absent signature, policy drift, stale base and expiry refused |
| Untrusted checks | Actual source test success, actual failing test/validator rejected; untrusted candidate cannot access owner policy, host credentials or a network interface |
| Exact transition | Old/new/source policy SHA-256 checked; `git update-ref` CAS refuses concurrent changed `main`; independent readback and source log hash retained |
| Actual owner-host acceptance | Distinct OS accounts, reviewed hook installation, owner-signed live promotion through restricted Git ingress, independent read-only verification and offline restore |
| Customer/FCIS production | **Not part of H3.** No OAuth/MCP/Go deployment, MIDI2 release, Store grant or legal certification |
