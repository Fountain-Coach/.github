# Internal FCIS owner OpenAPI — maintenance protocol

**Scope:** Maintain the existing *internal, FCIS-owned* API contract, not a vendor/official upstream OpenAPI dependency or a second HTTP authority. This procedure is a reusable part of **FCIS Owner Access**, not a new FCIS-KIT capability, protocol, client, service or plugin.

## Semantic operation authoring and registry-backed capability discovery

An FCIS OpenAPI operation is written to be *selected by a person or reasoning client*, not merely decoded by an HTTP library. Apply the same progressive-discovery rule as Skill Creator: a compact stable name and meaningful description select the relevant operation; detailed schemas and examples guide its actual use. This does **not** make OpenAPI the FCIS instrument registry, MIDI2 IDL, or Host permission authority.

| Required dimension | Existing authority | Required human/machine projection |
| --- | --- | --- |
| HTTP management operation | Current `FountainHostMCPOAuthHandler` route and OpenAPI 3.1 | Unique stable `operationId`, action-oriented `summary`, explanatory `description` with when to select and when not to use cues; real parameters, JSON Schema and status codes |
| Instrument purpose and available actions | MIDI2 IDL, FCIS-KIT declared instrument identities, signed installed Host registry | Purpose, usable intent, exact capability/operation ID and version, target, typed inputs/results, side effects, bounded execution and evidence obligations |
| Availability and authority | Current target route, signed issuer admission, Host execution registry, scoped client grant | Distinct `declared`, `installed`, `admitted`, `routable`, `authorized-for-this-client` and `callable` claims; source and observation identity for positive claims |
| Client-facing tools | Actual MCP adapter `tools/list` and `tools/call` | Semantic tool descriptions and input schemas derived from the same admitted operations; explicit mapping back to IDL/Host identity; recheck grants at dispatch |
| Outcome | Terminal Host result plus FountainStore receipt and independent witness | Explicit success/refusal/error distinction, job and correlation IDs, provenance/evidence references, NOT_ESTABLISHED when live proof absent |

**Selection-language checklist (every operation):** State what user goal makes this operation appropriate, what it does *not* do, which subject/client/Host it applies to, required authentication and operation grant, read-only versus mutating effects, approval/cost/rollback when relevant, where typed outputs come from, what failures mean, and how the result is independently verified. Keep `operationId` stable across revisions (version incompatible changes), `summary` brief, `description` readable, `tags` meaningful, `$ref` schemas truthful, and HTTP examples free of credentials and private infrastructure. Do not pad the LLM's initial discovery context with full opaque schemata: provide concise discoverability and detailed contract inspection on selection through already admitted interfaces.

**No arbitrary capability ceiling:** The currently checked-in `OwnerFleetHost.capabilities.items.enum` accepts only `host.describe` and `FountainHostMCPAdapter` explicitly handles a few tools. These are **source limitations**, not a lasting security requirement or complete census of the Host. Change those shapes **only together with actual native, typed, authorized implementation**. Refuse a claimed fleet-wide API projection that silently excludes another admitted callable operation, but do **not** weaken today's deployed per-client grant or invent operations merely to satisfy a larger document. A narrow source status remains narrow until the registry-backed projection and tests exist. The authorized dynamic inventory must come from the Host/issuer evidence, not a list hand-maintained in an OpenAPI enum, UI JavaScript, Skill paragraph or model prompt.

**Callability is a real-time, target/client-specific predicate:** An instrument being declared, installed, or enrolled does not grant use. Only report currently callable when implementation, admitted release, executing target route, current client/operation grant and bounded input contract are verified together. Distinguish reachable/healthy/last-seen observations from enrollment; never fabricate one from the other. Negative or missing evidence must be typed as refused or NOT_ESTABLISHED. Discovery itself must not mutate or confer authority.

**Preserve existing protocol owners:** OpenAPI governs HTTP owner management; MCP governs its own tool transport; MIDI2/FCIS-KIT defines instrument identity and typed operation/lifecycle. A Host may expose the same admitted operation through more than one transport; map one identity, but do not generate a new HTTP endpoint for every instrument, duplicate the registry, or make MCP OAuth identity a replacement for Host authorization.

**Required deterministic checks for an implemented change:** Enforce unique semantic `operationId`/nonempty distinct `summary`/`description` on each HTTP operation; valid OpenAPI 3.1 `$ref`, actual wire schemas/security/origin/refusal and version compatibility. For a Host-capability projection, compare the issuer-admitted target and native Host instrument set, operation IDs/versions and input/output contracts against the OpenAPI inventory and MCP `tools/list` **for the same client, grant, source revision and target**. Verify `tools/call` succeeds only when admitted, and refuses unauthorized, stale, revoked, unknown, wrong-target and changed-release operations. Assert a newly admitted extra instrument is discoverable without editing a fixed `host.describe` allowlist; assert a merely declared/unadmitted instrument cannot be called. Assert connection, execution, persisted terminal and live-client acceptance are reported separately. Until these tests and their real source implementation exist, report the dynamic projection as NOT_ESTABLISHED—not passed.

## For each proposed API change

1. **Resolve scope and current truth.** Read the current domain `AGENTS.md`, `PLANS.md`, published Governance 07/08/142/152/160/161 and the checked-in OpenAPI guide. Identify the one operation and current source SHA; inspect Swift dispatch, actual type definitions, matching tests, current Press callers, the exact Caddy route (where deployed), and previous acceptance evidence. Decide whether the request changes contract only, Swift behavior, Access consumer, or a separately authorized release. Do not infer implemented behavior from a proposed schema.
2. **Preserve independent authorities.** FountainAuthKit owns owner authentication, OAuth grants and revocation; signed issuer/FountainStore records own machine admission; Host owns execution and terminal evidence; Press reads and operates these APIs but maintains no parallel permission or machine database. A passkey session is not a Host grant. Do not infer online/healthy/last-seen from `authorizationState=verified`, or treat `approved-pending-channel` as enrolled.
3. **Change only the corresponding route and OpenAPI entries.** Keep semantic operation descriptions and any registry-backed capability projections source-aligned; do not rewrite deployed wire formats or hardcode a second list. Match exact path, method, operationId, security scheme, allowed `Origin`, headers, request fields, Swift `Codable` response fields, optional/omitted values, errors, `$ref` and implementation/deployment status. Maintain `x-fcis-not-admitted` as **metadata only**, never speculative paths or SDK methods. Do **not** replace distinct fleet inventory with `host.describe?inventory=1` or rewrite standards-based OAuth discovery/PKCE as a private format. Respect existing `Date` encoding: Fleet and Host observation times are ISO strings; older Swift `Date` Codable values are numeric Foundation reference-date seconds unless their actual encoder changes.
4. **Enforce the security negative cases.** `GET /oauth/owner/hosts` and owner pairing require a real owner **passkey** session; legacy Basic must not bypass that requirement. Owner pairing uses allowlisted `Origin`, exact body and `x-fountain-owner-intent` for decisions. Signed device `/oauth/host/enrollment/prove` and `/activate` prohibit browser `Origin`, `Cookie`, and `Authorization`; they do not become owner-session operations just because an error status overlaps. Host target IDs must be issuer-admitted opaque identifiers, not hostnames, IPs, or URLs. Refusals and unavailable Store evidence fail closed and must not look like successful enrollment or revocation.
5. **Version the interface.** Update `info.version` using the source guide: major for incompatible wire/auth changes, minor for admitted additive features, patch for clarifications. A proposal may be marked not-admitted without an HTTP path; addition requires the native Kit/Host authority and tests first. Keep the spec internal and free of actual owner account IDs, private IPs, tokens, machine keys and Store snapshots.
6. **Verify at both boundaries.** Include a focused semantic-name/description and capability-state regression where the relevant native projection is implemented; metadata-only tests never establish runtime dispatch. From the domain repository root run `node --test apps/estate-publisher/Tests/fcis-owner-openapi.test.mjs` and `git diff --check`. Run the native focused Swift suite against the **same source revision** in an isolated Ubuntu/Swift environment: `swift test --package-path apps/estate-publisher --filter 'FountainHost(OwnerOpenAPIContract|OwnerTarget|OwnerPairingHTTP|MCPAuthorizationOwnerHTTP|MachineEnrollment)Tests'`. Include both valid and refused real handler response JSON (200/201, 400/401/403/404/409, 503 as applicable); use synthetic records only when clearly labeled. Follow up with Press JS/Python and browser tests only when the consumer changed. If a test cannot run, report its exact prerequisite instead of substituting a mock acceptance result.
7. **Reconcile release as a distinct operation.** A green OpenAPI file is **source conformance only**. Before production, compare the existing signed issuer executable and exact Caddy matcher/digest and release policy. Release the issuer and URL matcher with predecessor, rollback and HTTPS readback **before** its dependent Press fleet view. Observe real owner-passkey browser access, foreign-origin/unauthenticated refusal, admitted Host identity, and independent FountainStore/Host job receipts. A browser mock, HTTP 200, successful PR or GitHub marketplace version is not production or physical-iPad acceptance.
8. **Close with provenance and source ownership.** Commit code, contract, tests and evidence on the correct domain PR; update the domain `PLANS.md` and the Press consumer's pinned contract revision when relevant. Record source SHA, contract version, tested operations and failures, CI/native result, deployed revision/receipts or `NOT_ESTABLISHED`, and next smallest unfinished gate. Do not silently merge, deploy or claim hosted Skills changed.

### Example triggers

- “We added a new host observation field; update FCIS OpenAPI and check Swift parity.”
- “The fleet endpoint now returns 401; verify the contract and passkey/CORS refusal.”
- “Prepare a backward-compatible owner grant response change and its contract tests.”
- “Verify the signed issuer/Caddy fleet release is consistent with OpenAPI.”
- “A newly admitted Go instrument is not discoverable via FCIS; reconcile typed Host, OpenAPI and MCP projections without a new tool registry.”
- “Review operationId/summary/description so an LLM selects the right fleet operation without confusing enrollment with callability.”

**Not this workflow:** An external provider's *official* schema must follow `Fountain-Coach/.github/docs/FCIS-Official-OpenAPI-Dependency.md` with a pinned upstream digest. MIDI2 IDL or generated reasoning-contract changes follow their own Kit/IDL and `generated-contract-regeneration` procedure; changing OpenAPI does not supersede them.
