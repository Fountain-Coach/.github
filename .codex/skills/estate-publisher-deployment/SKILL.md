# EstatePublisher Deployment — governed lanes

This skill is a procedure, not a runtime publisher. Its **only canonical skill authority is Fountain-Coach/.github** (Governance Chapter 160); EstatePublisher's installed executable and Swift Kits own effects. Begin with [FCIS Goal Fidelity](https://github.com/Fountain-Coach/.github/blob/main/docs/FCIS-Non-Invention-and-Goal-Fidelity.md) and current [Governance Chapter 158](https://governance.fountain.coach/chapters/158-publishing-is-not-a-distributed-transaction/).

## Resolve the actual operation

1. Fix the writer's observable goal, approved host and route, exact authored source and rights, and finite acceptance. Distinguish private preview, immutable static publication, mutable FountainStore operation, service deployment, and DNS/TLS changes.
2. Inspect the working owner Git revision, deployed predecessor, present EstatePublisher implementation and receipt. **Do not substitute stale repository mirrors, historical experiments, or a saved command for active operational authority.**
3. Apply the FCIS four-question necessity test: what goal, what observed failure, which existing contract makes an alleged prerequisite necessary, and what smallest same-path correction? Unproved requirements are non-blocking. Do not turn a static essay into a distributed application transaction.
4. Read [deployment modes](references/deployment-matrix.md) and choose the current admitted mode. One mode's resolver is not a universal publishing requirement.

## Immutable static public publication — Chapter 158

Compile → validate → package → deliver → activate → verify, through the existing *authenticated* EstatePublisher SSH/SFTP/rsync and Caddy profile where supported. **Remote FountainStore replication, MIDI 2.0 sessions, host agents, new signing/enrollment ceremonies and a continuously running coordinator are not prerequisites.**

- **Compile and validate off-host:** approved route/rights and media, current source-owned Publication Core, semantic relationships, canonical/social metadata and the actual public predecessor. For a *new route*, reuse the current named template/preview scenario with that route as input, and verify inherited masthead, reel, active/Info, theme, footer, responsive geometry and links; do not copy a single old HTML fragment or fabricate a scenario for every essay. A scenario-definition test does not prove a live visual witness.
- **Package:** immutable approved artifact, exact SHA-256 inventory, intended host/root/changed routes, prior release and rollback. Preserve all unrelated published routes and private data.
- **Deliver and activate:** invoke the existing native publisher using its real authorized deployment identity, host verification and bounded target. Check current Caddy route admission; include the smallest necessary validated route allowlist change with the release. Stage outside the active root, verify bytes, atomically switch current, retain predecessor and reload Caddy only when needed. Do not use arbitrary root SSH mutations or bypass real authorization.
- **Verify:** native terminal receipt and independent HTTPS bytes for the new page, opening/social image, audio and representative neighbors; check metadata and the active release/rollback. Where the writer asks about visual behavior, separately prove AX/WebKit/Safari rendering. Stop on verified success.

## Other production and interrupted operations

Mutable Store-backed routes may require `estate.publication.sync` and its native typed Store operation; services, identity and DNS/TLS require their own currently admitted commands. **Never impose those prerequisites on an otherwise authorized immutable static release, nor replace a genuinely managed operation with ungoverned static copying.** Read the live native operation contract and its permission boundaries.

When interrupted or failed, inspect the persisted terminal receipt and active identity before retrying. Preserve the previous release, use its supported idempotency/resume contract if available, and avoid overlapping processes or repeated credential prompts. A keychain prompt, source commit, tested proposal, running process, or homepage HTTP 200 does not prove deployment.

## Owner-controlled WLAN

Use [WLAN staging](references/wlan-staging.md), confirm the registered Ubuntu Mac mini's actual current release and keep this private. Require HTTPS for WebAudio AudioWorklet when the browser needs it; do not impose production ceremonies on a disposable preview.
