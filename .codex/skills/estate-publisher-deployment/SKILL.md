# EstatePublisher Deployment — governed lanes

This skill is a procedure, not a runtime publisher. Its **only canonical skill authority is Fountain-Coach/.github** (Governance Chapter 160); EstatePublisher's installed executable and Swift Kits own effects. Begin with [FCIS Goal Fidelity](https://github.com/Fountain-Coach/.github/blob/main/docs/FCIS-Non-Invention-and-Goal-Fidelity.md) and current [Governance Chapter 158](https://governance.fountain.coach/chapters/158-publishing-is-not-a-distributed-transaction/).

## Fountain Press standard: one source-bound composition for staging and production

**Writer-adopted 6 November 2026.** Fountain Press is the standard **publication-composition and reading presentation** for every admitted book/essay/Governance edition in *both* canonical WLAN staging and public production. An approved work is projected once from the exact source-owner Git commit into the existing Press manifest/Bookshelf/Linotype Reader and its immutable artifacts. The production handoff reuses the verified Press composition and pinned source/asset identities (with declared stage-only URL transforms), **never** invents a new production Reader or republishes a short chapter sampler as a complete book. Nonbook Teatro/other service surfaces keep their native bodies while following their approved publication-shell and custody contract; Press does not seize their functionality or private-media rights.

**Authority boundaries remain unchanged:** source owners retain text, statuses, illustrations, links and rights; Reframe/FountainStore retains any writer Bookshelf admission; Fountain Press composes the edition; **EstatePublisher alone** authorizes/delivers/activates immutable staging and public release, records terminal receipts and preserves rollback. Production requires distinct approval and independent HTTPS/asset/metadata acceptance. A stage URL, Git push, local Press build, source digest or passed browser tests are not public publication receipts.

For the current tested pattern, inspect the 6 November 2026 **Governance v162** admission: 160/160 original chapters, 72 current/88 reference classifications, 70 retained source figures, 1,132 original links and 160/160 live browser compositions; one original Press compositor, source-lock SHA, immutable v161/v160 rollback and independent HTTPS HTML/JS/receipt digests. This is a **verified owner-WLAN stage**, not a public or physical iPad/VoiceOver proof. Apply this evidence model to the *actual scope* of each edition rather than imposing those fixed counts. Read [WLAN staging](references/wlan-staging.md) and [deployment modes](references/deployment-matrix.md) before promotion.

## Agent-readable publication release check (when declared)

For a publication with an adopted or explicitly requested machine-readable interface, inspect the Fountain Press source/edition manifest and its public agent guidance before package, stage or release. Require the **same source owner, revision, edition identity, publication state, complete entry ordering, exact source SHA/status and guidance digest** in the human and machine projections. For Governance, preserve all current/reference statuses, original links and source identities; never call a historical/reference chapter a current instruction. Reject fabricated tool permissions, stale agent guidance, unsupported APIs, private `AGENTS.md` exposure, private media and unauthorized access claims. The [Fountain Press machine-readable publication procedure](../linotype-estate-template/references/agent-readable-publication.md) and its offline validator provide a bounded check, **not** proof of legal rights or running publication.

Stage the machine discovery route and guidance alongside the **same immutable Press artifact**, verify their actual HTTPS bytes with a non-browser reader and separately verify Linotype navigation. On production, require distinct author/publisher approval and independent public readback of the same versioned machine and human surfaces, with rollback. If the machine interface is not part of the adopted/requested scope, report it as not established rather than inventing a deployment blocker or new service.

**Governance-specific writer decision, 6 November 2026:** Neither an authored diagram nor a generated hero, chapter image, 1200×630 social card or first-page screenshot is a release prerequisite for `governance.fountain.coach`. **Do not reject Governance** because images are missing, count illustrative figures as normative authority, or require replacement of historical generic Open Graph art. Reader success does not certify social-card success; the v163 70-figure fix is not evidence that the earlier 89 generic Governance Open Graph fallbacks were replaced. ## Immutable static public publication — Chapter 158

Compile → validate → package → deliver → activate → verify, through the existing *authenticated* EstatePublisher SSH/SFTP/rsync and Caddy profile where supported. **Remote FountainStore replication, MIDI 2.0 sessions, host agents, new signing/enrollment ceremonies and a continuously running coordinator are not prerequisites.**

- **Compile and validate off-host:** approved route/rights and media, current source-owned Publication Core, semantic relationships, canonical/social metadata and the actual public predecessor. For a *new route*, reuse the current named template/preview scenario with that route as input, and verify inherited masthead, reel, active/Info, theme, footer, responsive geometry and links; do not copy a single old HTML fragment or fabricate a scenario for every essay. A scenario-definition test does not prove a live visual witness.
- **Package:** immutable approved artifact, exact SHA-256 inventory, intended host/root/changed routes, prior release and rollback. Preserve all unrelated published routes and private data.
- **Deliver and activate:** invoke the existing native publisher using its real authorized deployment identity, host verification and bounded target. Check current Caddy route admission; include the smallest necessary validated route allowlist change with the release. Stage outside the active root, verify bytes, atomically switch current, retain predecessor and reload Caddy only when needed. Do not use arbitrary root SSH mutations or bypass real authorization.
- **Verify:** native terminal receipt and independent HTTPS bytes for the new page, opening/social image, audio and representative neighbors; check metadata and the active release/rollback. Where the writer asks about visual behavior, separately prove AX/WebKit/Safari rendering. Stop on verified success.

## Other production and interrupted operations

Mutable Store-backed routes may require `estate.publication.sync` and its native typed Store operation; services, identity and DNS/TLS require their own currently admitted commands. **Never impose those prerequisites on an otherwise authorized immutable static release, nor replace a genuinely managed operation with ungoverned static copying.** Read the live native operation contract and its permission boundaries.

When interrupted or failed, inspect the persisted terminal receipt and active identity before retrying. Preserve the previous release, use its supported idempotency/resume contract if available, and avoid overlapping processes or repeated credential prompts. A keychain prompt, source commit, tested proposal, running process, or homepage HTTP 200 does not prove deployment.
