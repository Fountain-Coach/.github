# Linotype Estate Template - FCIS-governed procedural projection

This skill explains how to conduct the work; it does NOT certify all FCIS chapters, create authority, define a new runtime capability, or supersede a typed Kit. Read [FCIS authority and reconciliation](references/fcis-authority-and-reconciliation.md) at the start of any implementation, publication, conformance, or architectural claim. The user's requested observable outcome fixes scope; the actual system fixes state.

## Mandatory read–write continuation of the owning PLANS.md

**Before proposing a plan, writing implementation/source files or staging a change, read the existing `PLANS.md` in the owning repository.** Identify the accepted scenario, active phase, actual last evidence, known gaps and **next uncompleted action**. A request to "proceed" means resume that phase; never start another plan, scenario or DoD simply because a conversation or session restarted. If no plan exists, establish that absence before creating the smallest phase record required by the existing repository contract.

**Maintenance is part of execution, not a closing note.** For governed source-affecting work, write a continuation to that **same active `PLANS.md` phase before the first source modification**, recording the unchanged author goal, applicable governance, current observed state, the bounded source slice, verification and reversal. **At each material state transition**, update the same phase with the actual source revision, test result, release/receipt/readback, failed operation or changed next step; classify OBSERVED, PROVEN, DOCUMENTED, INFERRED and PROPOSED correctly. **Before handoff**, write the truthful completion/partial/failure state, evidence addresses, remaining original DoD and the next executable action. Re-read after another actor's changes before writing so their progress is not overwritten. Do not label plan text as live acceptance.

For read-only questions or advice that makes no governed source or runtime change, read the existing plan as relevant but do not create a gratuitous entry. If the required plan write fails, report the exact write failure and the unrecorded status; do not claim plan maintenance or replace it with chat prose. A missing plan record is not permission for an unrelated new subsystem. Never ask the writer to repeat an already settled "proceed".

## Start with a bounded decision

1. **Restate the concrete requested outcome and finite acceptance.** Do not change a viewing request into a deployment, a website fix into an architecture project, or Bookshelf admission into public release. New ambitions are separate follow-ups.
2. **Inspect the currently working path.** Identify the named Git source owner, branch and exact SHA, complete direct-static route, local preview, production HTTPS readback, canonical staging registry and *actual active stage symlink/service*. The registry's last observed release is historical when it disagrees with live state. Record last accepted evidence and failures as OBSERVED / PROVEN / DOCUMENTED / INFERRED / PROPOSED. Never replace live bytes with arbitrary latest `main`.
3. **Resolve applicable FCIS.** Read the organizational [Goal Fidelity and Non-Invention rule](https://github.com/Fountain-Coach/.github/blob/main/docs/FCIS-Non-Invention-and-Goal-Fidelity.md), applicable sections and amendments of [published Governance](https://governance.fountain.coach/), current repo instructions and typed Kit/Store/EstatePublisher authority. Record version/commit, publication status, conflicts and inaccessible sources. Never mistake a static reference or local draft for the accepted current rule. This is scoped source reconciliation, not an invented universal compliance service.
4. **Detect the Invented-Prerequisite Loop before declaring a blocker.** Apply the four-question FCIS test: original observable goal; actually failed operation; why the working mechanism is insufficient; smallest correction with same-path acceptance. The loop is *goal substitution -> speculative prerequisite -> implementation -> passing tests used to claim necessity -> new dependency -> moving Definition of Done*. If the new necessity is unproven, reclassify it as PROPOSED/NON-BLOCKING and continue on the existing proven path. Read [the named loop and EstatePublisher incident](references/invented-prerequisite-loop.md). Do not make the writer an operator or test harness.
5. **Select the owner boundary.** Reframe/FountainStore own author-approved Bookshelf membership; Fountain Press Linotype owns book rendering; Fountain Coach Publication Core governs complete, checked-in, direct-static routes; EstatePublisher owns governed previews/check-in and public promotion; deployed HTTPS/WebKit is a *read-only* observation authority. Read [development / staging / production](references/development-staging-production.md) whenever an estate environment or staging transition is in scope, [publication lanes](references/reframe-publication-lanes.md) for Bookshelf or release tasks, [template contract](references/template-contract.md) for shell/layout questions, and [bounded implementation guidance](references/implementation-prompt.md) only for a demonstrated defect.
6. **Keep the three authorities distinct.** **Development = Git** (source owners, exact commits, intended changes), not a DNS-based environment. Its browser view is the existing lease-bound native local preview. **Staging = the single registered owner-WLAN Ubuntu Mac mini** with an immutable release and active symlink. **Production = currently deployed public HTTPS bytes and separately retained publisher receipts.** Production observes published reality; it does not overwrite authored Git or grant editorial rights. Do not provision `dev.*`, a new DNS entry, a fourth service or an alternate publisher to represent development.
7. **Apply production-first lineage only to the requested canonical Git-to-staging transition.** See [development / staging / production](references/development-staging-production.md). The author explicitly wants the selected published production state to be the starting point for a development-derived staged candidate. Independently verify the *affected route/asset scope* using existing production release inventories and observed HTTPS bytes; reuse a valid immutable baseline rather than force a redundant import or a whole-estate crawl for a route-scoped change. Record exact Git owners/SHAs, intended delta, preserved content and WLAN-only transformations. Compose the candidate off-line, then check the production and staging predecessor again before using the already-established EstatePublisher SSH/rsync + SHA-256 + atomic symlink + readback path. Never activate bare production as a temporary public staging state or erase retained stage work. Staging inspection and local Git previews require no production-first ceremony.
8. **Separate the requested guarantee from ordinary publication, and preserve the established SSH contract.** Inspect the installed EstatePublisher implementation, not only an open PR. Its historical `previousReleaseID` checks the stage predecessor but does not alone prove the production baseline. When the writer explicitly requires a *guaranteed* production-first transition, do not certify that guarantee without observed native checks and correlated evidence; address a demonstrated missing check by the smallest change in the existing EstatePublisher client/contract. **Do not freeze an otherwise authorized, working static publication merely to install that proposed check**, unless the specific requested outcome depends on the guarantee. Existing authenticated OpenSSH, rsync, SHA-256, atomic symlink activation, rollback and independent readback are the accepted transport; do not require a new restricted account, signing ceremony, helper, SecretStore enrollment, daemon, GitHub CI, DNS zone or permission refactor absent the FCIS four-question proof. The skill cannot impersonate runtime enforcement or independent publication authority.
9. **Verify claims relevant to the goal.** Structural HTML helper: `python3 scripts/check_shell_snapshot.py --contract <accepted-contract.json> --site estate=<staged-html> ...`. It tests a *declared static fixture/schema*, not lineage, FCIS, CSS, WebKit, rights, deployability or production. For visual parity use existing EstatePublisher/WebKit mirror and native Safari/iPad evidence where necessary. For a **new** public route, first reuse the accepted domain template and applicable named preview/scenario acceptance; check inherited navigation, active state, Info, theme, footer, visual geometry and relationships before packaging, as described below. For a stage transition, keep production-source verification, candidate inventory, live stage receipt and browser/readback evidence separate.
10. **Publish publicly only under separate authorizing intent.** WLAN staging is not production. Production takes an already-built immutable digest-bound artifact through an authorized EstatePublisher plan, preserves rollback, and is confirmed with typed receipts and independent public readback. Never build on production, copy private Satzfunk media/tokens, or claim public publication from stage, Git push or HTTP 200 alone.
11. **Stop when the requested outcome is proved.** Report separately source state, baseline lineage, declared Git delta, stage predecessor/current release, native enforcement state, tests, browser witness, public release, and open uncertainties with links, SHAs, receipts and exact bounded failures. Never claim universal FCIS compliance or a production/staging transition not actually verified.

## New public route: scenario reuse before publication

For requests such as "publish this new essay," **compose the inherited Fountain Coach Publication Core before releasing the route**. The new route is an input to an already-adopted template/preview scenario; a new scenario is **not** created merely because a new URL exists.

1. **Resolve the adopted source, not a convenient HTML specimen.** Identify the current domain-owned Git revision, declared route identity and approved Publication Core shell revision, then the established estate template/preview scenario and its owner. Inspect the accepted public navigation/rights/Info behavior and actual layout; a historical nine-item reel, local screenshot, icon count, or cross-domain design proposal alone is not binding.
2. **Compose the final direct-static page in its owner repository.** Preserve the publisher masthead, editorial reel order and destinations, active/focus states, responsive CSS and icons, theme toggle, breadcrumbs, four-part legal/provenance footer, canonical/social artwork and existing content. Preserve the domain's authored text, media and distinct role. Do not hand-copy a navigation fragment and call it template inheritance; verify against the pinned source and shared semantic/visual contract.
3. **Execute the closest *existing* acceptance.** Use the currently available named preview/template reproduction scenario and route-parameterized accessibility/WebKit/visual comparison. Check reader navigation and Back, mobile/iPad portrait and landscape, light/dark/Info where supported, resolved public links and rights, and the route's media and social image. A unit test that describes the scenario is **not** its live AX or visual witness. Bind accepted evidence to this exact source, route, shell revision and candidate.
4. **Reconcile and release the finite change.** Compare the affected collection, cross-links and existing public routes against the actual released predecessor. After source and relevant acceptance, publish through the already-admitted static or managed EstatePublisher mode, with bounded digest/rollback/public readback. Do not make new machinery, whole-estate reproduction or a new per-essay scenario an invented prerequisite; report any *genuine* missing witness as unverified and apply the FCIS four-question test before blocking an otherwise authorized route.

For implementation details load [the bounded remediation playbook](references/implementation-prompt.md) and [the current template contract](references/template-contract.md). The Chapter 127 Publication Core is an **authoring contract**, not a deployed runtime page generator; the Chapter 119 scenario factory composes existing scenarios, not fictional per-route capabilities.

## Specific publication and shell invariants

- **Book is not page.** A source revision, composed folio, Empty slot, score, player and public edition are distinct identities. An Empty becomes a book only after an attributed authorized writing/admission act. Reframe Bookshelf membership never implies DNS, a reel icon or public redistribution.
- **One publication authority, no generated web shell at runtime.** Chapter 127 describes a versioned Fountain Coach Publication Core embodied in the complete checked-in static HTML/CSS/JS of each route, not a new wrapper or generator. A measured Linotype reader is a source-bound book compositor; it is not the global site shell.
- **Shared estate semantics, independent authored bodies.** Preserve the source owner, masthead, approved editorial navigation, focus/active states, footer rights/provenance and responsive behavior. A pinned historic nine-item reel is only binding when the current adopted route/manifest proves it; unresolved public destinations must not be invented. Status remains a supporting/legal surface according to current policy.
- **Different kinds of proof remain different.** Identical link lists do not prove shared visual geometry; a screenshot does not prove source identity, Store admission, accessibility, media rights or public release.
- **Production-first is a lineage relationship, not two visible deployments.** Reuse a verified production baseline off-line; a candidate for the author-requested production-first stage is baseline plus explicit Git delta. A stage predecessor check proves only stage concurrency. Missing lineage proof means *guarantee not established*, not automatically "SSH publishing is broken" or "install new security machinery". See the [Invented-Prerequisite Loop](references/invented-prerequisite-loop.md).

## Examples

- **"Show the staging estate"**: read `Fountain-Coach/estate/staging/environment.json` and the actual running release, then provide the verified, copyable WLAN entrance. Do not provision, publish or create a new test suite to answer a viewing request.
- **"The Governance reel is inconsistent"**: reproduce the exact domain transition and compare current DOM/CSS/visual witness against the adopted shell revision. Repair the smallest source-owned static projection; do not create a new shared runtime renderer merely because an older spec proposed one.
- **"Admit a manuscript to the Bookshelf"**: verify writer intent/source digest/Store membership, then show the real Press cover/reader and reopen; no automatic domain or public website.
- **"Update canonical staging from development"**: use existing verified production baseline for affected routes, reconcile the exact Git delta, check stage predecessor and invoke the existing EstatePublisher SSH delivery contract. If native lineage enforcement is absent, state *the requested guarantee is not yet proved*; propose only the minimal client-side correction and do not replace SSH delivery with security theatre. Do not claim skill prose enforces a live transition.
- **"Do we need dev.fountain.coach?"**: no. Git is development; native local FountainStore preview is enough unless a separate, demonstrated origin-dependent requirement justifies a DNS endpoint.
- **"Release the complete estate"**: only under separately authorized release scope, reconcile exact static routes and owners, use existing typed EstatePublisher operations, and verify selected public readbacks. No production compilation.

Use the FCIS [Invented-Prerequisite Loop](references/invented-prerequisite-loop.md) diagnostic before expanding the workflow. Protect real authorization and SHA/digest/rollback evidence; never mistake extra ceremonies or passing tests for the necessity of a new system. Stop when the originally requested result is proved.
