## New route and template acceptance

Resolve the owning source and accepted **Fountain Coach Publication Core** (Governance Chapter 127), and for book-shaped editions the canonical **Fountain Press** manifest and measured reader, before composing any new direct-static route. Do not give staging a different book engine from public production; distinguish Press presentation from EstatePublisher release authority. Reuse an **existing** template/preview scenario, parameterized by the new route, and check the adopted navigation, Info, theme, footer, responsive rendering, semantic graph, media and canonical/social image. An old nine-item reel specimen or a unit test that mentions an intended scenario is not a live browser acceptance. No new scenario per essay is presumed necessary. A missing executor must be named honestly and evaluated against the FCIS four-question requirement test; it must not automatically block a functioning, authorized static lane.

## Blocker test (FCIS)

State original user outcome; exact failed current operation; applicable binding requirement; minimal existing-path repair and acceptance. If evidence is missing, mark a hypothesis **NON-BLOCKING**. Do not develop new Store replication, approval, host agent, MIDI transport, security ceremony or universal test service to rationalize a guessed failure.

**Static sequence: compile → validate → package → deliver → activate → verify.** Do not mistake Git push or local staging for public release.
