## Repeatable procedure

1. **Inspect current identity and actual failure.** Inspect issuer metadata, running Host adapter, published Access JS, credential *metadata only*, current source SHA and current authorization; do not request, dump, paste, log, display or commit any password, Basic header, signing key, bearer/refresh token, passkey secret or SSH private key. Do not reset user credentials or disturb the existing ChatGPT grant.
2. **Bind the existing owner.** Register passkeys only following an independently verified owner action, associating the WebAuthn credential with the existing issuer subject; do not invent a second account, local permission store or login domain.
3. **Use vetted WebAuthn/FIDO2 verification.** On the issuer's chosen HTTPS origin, require fresh unpredictable challenge, correct Relying Party ID, origin, credential public key/signature, user verification, expiration, replay resistance, and rate limiting. Verify `access` vs `fcis` origins explicitly, default to an issuer-hosted top-level ceremony and avoid homemade authentication crypto.
4. **Preserve OAuth.** Apply [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), exact registered redirect URIs, authorization-code + PKCE S256, resource audiences, bounded consent, existing signing/grant/refresh continuity and denial after revocation. Never turn human login into automatic Host power.
5. **Select secure browser sessions.** Follow [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html); evaluate a same-origin backend-for-frontend that holds OAuth tokens server-side and issues an opaque Secure/HttpOnly/SameSite cookie. Require CSRF defense, timeouts, logout, reauth/step-up, and negative browser-origin tests. A session cache is not another authority. Never put credentials or grants into static Press content or localStorage.
6. **Establish independent recovery.** Enroll a second usable authenticator with recent owner verification, revoke lost devices, prove second-device login and define a reviewed lost-all-device procedure. Keep existing Basic fallback controlled and audited during migration; retire it only after replacement and recovery are independently accepted. No unverified email/SMS shortcut.
7. **Implement in bounded source-owning slices.** Host/Kit own the verifier and authority; Press owns the user interface; Host/Store own effect receipts. Do not invent a second service, new `mcp.fountain.coach` front end or dead UI controls.
8. **Run the acceptance matrix.** Verify isolated WebAuthn wrong origin/RP/challenge/key/UV/replay denial, cookie/CSRF/logout/expiry tests, sign-in from an eligible *physical* enrolled device (including iPad Safari), accessibility, second-factor recovery when separately in scope, existing ChatGPT `host.describe`, and distinct disposable-client revoke -> refresh denied -> real MCP denied -> Store receipt. **No specific Mac device is an acceptance precondition for headless Hetzner cutover.** Simulated iPad viewports support but do not replace native testing.

## Reasoning-expressive Host and instrument discovery — mandatory

Apply Skill Creator's **name/description selection** principle to FCIS operations. The internal FCIS owner OpenAPI 3.1 contract is the **human- and machine-readable HTTP management projection**, not the FCIS-MIDI2 capability authority. Read [the FCIS OpenAPI maintenance protocol](references/openapi-maintenance.md) before any operation/capability change.

1. **Describe intended use, not just implementation.** For each existing HTTP operation use a stable, meaningfully named `operationId`, a short action-oriented `summary`, and a `description` explaining *when to select it*, *when not to*, required subject/client/target and scope, read versus mutation consequences, expected typed result and failure/evidence semantics. Explain parameter meaning and real constraints in OpenAPI 3.1 JSON Schema. Give safe examples when they aid selection. Do not rename shipped IDs or wire fields without compatibility/versioning.
2. **Discover the actual capabilities.** Resolve the signed/typed MIDI2 IDL, FCIS-KIT instrument contract, installed Host registry, target routing, issuer admission and per-client grant. The HTTP inventory and MCP `tools/list` are distinct projections of that authority, not handwritten substitutes for it. Only expose operations actually implemented and registered on the selected Host; preserve their canonical identities and versions in both projections. A broad Host description or an `OpenAPI` operation is not an executable grant.
3. **No hardcoded `host.describe` capability ceiling.** Treat today's `OwnerFleetHost.capabilities.items.enum = ["host.describe"]` and the MCP adapter's special-case list as **current implementation limitations**, never as constitutional FCIS capability policy. A new admitted, authorized operation must not require writing a second inventory by hand. Reconcile registry-backed HTTP capability metadata with MCP advertised tools, typed arguments and runtime dispatch **through existing native adapters**. Until supported and tested, label any extension NOT_ESTABLISHED; do not invent endpoints, auto-grant permissions, or present unimplemented tools as callable.
4. **Keep capability states independent.** Distinguish `declared`, `installed`, `admitted`, `routable`, `authorized-for-this-client`, `callable`, and `live-accepted`; attach source revision, issuer/Host observation time and evidence identity to positive claims. A machine can be enrolled yet offline; an installed instrument can lack a grant; a documented operation can lack a deployed route. Unknown state is explicitly NOT_ESTABLISHED, never silently coerced to true/false or advertised as a success.
5. **Select productively, execute narrowly.** The LLM may choose among semantic descriptions and inspect a detailed contract progressively, but cannot infer permissions from names, suggest an unchecked generic terminal fallback, or derive a usable credential. The existing Host revalidates exact target, owner/client relationship, scope, operation, parameters, bounded effects and authorization **at invocation**. FountainStore and independent witnesses—not the chat transcript, OpenAPI document, MCP listing or HTTP status alone—establish terminal effects.
6. **Enforce drift gates before release.** Extend existing Node OpenAPI source-drift and native Swift handler tests, plus existing MCP/Host focused tests, to compare current issuer inventory, admitted operation IDs, schema/version mapping, `tools/list`, real dispatch and per-client refusal. Reject stale or hardcoded capability enumerations presented as complete, orphaned/invented operations, ambiguous semantic descriptions, unsupported state transitions and false callability/health claims. A new operation is DOCUMENTED only after contract parity; CALLABLE or LIVE-ACCEPTED require separately witnessed execution and Store evidence. Preserve the current production service and grants until the separately governed release passes.
